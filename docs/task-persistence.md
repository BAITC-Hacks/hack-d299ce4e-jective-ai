# Задачи в Supabase

Каталог использует реальные опубликованные задачи. Новая база остаётся пустой: миграция не добавляет демонстрационные записи. Черновики видны только владельцу; опубликованная карточка доступна посетителям каталога.

## Применить SQL

1. Сначала должна существовать `public.profiles` из миграции регистрации. Повторно создавать её не нужно.
2. Откройте проект Supabase → **SQL Editor** → **New query**.
3. Скопируйте **весь** файл [20260923000200_tasks.sql](../supabase/migrations/20260923000200_tasks.sql) и выполните его под ролью `postgres` один раз.
4. Затем в новом запросе выполните **весь** файл [20260923000300_task_workspaces.sql](../supabase/migrations/20260923000300_task_workspaces.sql). Он сохраняет промежуточную работу с AI, вопросы и ответы пользователя до публикации.
5. Запустите приложение командой `npm run dev`. Для API нужны уже настроенные `SUPABASE_URL` и `SUPABASE_PUBLISHABLE_KEY` в `apps/api/.env`. `service_role` не нужен.

Миграция создаёт таблицу, индексы, ограничения, триггер, RLS и публичное представление в одной транзакции. Если `tasks` уже существует, выполнение остановится, не удаляя данные. Не удаляйте существующие таблицы ради повторного запуска: сначала сравните схему.

## Что хранится

| Колонки                                           | Назначение                                                                                      |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `id`                                              | Положительный числовой ID, не превышающий безопасное целое JavaScript                           |
| `owner_id`                                        | Владелец из `auth.uid()`, ссылка на `profiles`                                                  |
| `request_id`                                      | UUID одного черновика/публикации; пара с владельцем уникальна для повторной отправки без дублей |
| `status`                                          | `draft` или `published`                                                                         |
| `original_description`                            | Исходное описание пользователя, приватное                                                       |
| `analysis_snapshot`                               | Приватный снимок вопросов, ответов и анализа для этой сохранённой задачи; версия 1, до 256 КиБ  |
| `title`                                           | Заголовок, 1–200 символов                                                                       |
| `context`, `need`, `users`, `data`, `constraints` | Содержание сформированной и отредактированной карточки                                          |
| `expected_result`, `success_criteria`             | Ожидаемый результат и критерии успеха                                                           |
| `business_contact`                                | Контакт заказчика, приватный                                                                    |
| `interaction_format`                              | Формат взаимодействия                                                                           |
| `industry`, `direction`, `tags`                   | Категории и до 10 тегов                                                                         |
| `score`                                           | Информационная оценка качества 0–100, не основание для прав доступа                             |
| `created_at`, `updated_at`, `published_at`        | Время создания, изменения и первой публикации, назначаемое базой                                |

Поля карточки ограничены 10 000 символами каждое; категории — 100, один тег — 50. Пустые необязательные поля сохраняются как `null`. Публикация требует исходного описания не короче 20 символов, заполненных `need` и `expected_result`. Запоздалое сохранение черновика не меняет уже опубликованную карточку, включая её содержимое. Повторная публикация обновляет ту же запись и не меняет время первой публикации.

В `tasks` сохраняется итоговая карточка задачи, в том числе внесённые пользователем исправления. При сохранении черновика или публикации API также копирует в приватный `analysis_snapshot` текущую анкету из рабочего состояния владельца с совпадающим `requestId`. Вопросы и ответы остаются связаны с этой задачей даже после начала новой. При открытии сохранённой задачи её анкета восстанавливается из этого снимка. Снимок обновляется при следующем сохранении той же задачи; это не журнал всех предыдущих версий.

В отдельной приватной таблице `task_workspaces` хранится **одна текущая рабочая сессия на бизнес-пользователя**: исходное описание, вопросы AI, ответы пользователя, полученная карточка и метаданные анализа. Это позволяет продолжить создание задачи после обновления страницы ещё до сохранения в «Мои задачи». `owner_id` — первичный ключ и владелец, `snapshot` — версионированный JSON-объект с числовым `version: 1` до 256 КиБ, `updated_at` — время обновления от сервера. Начало новой рабочей сессии меняет только этот активный снимок, а анкеты уже сохранённых задач остаются в `tasks.analysis_snapshot` отдельно.

## Доступ и приватность

- Таблица `tasks` доступна авторизованному пользователю только для чтения своих записей. Вставка и изменение также требуют роли `business` из защищённой таблицы `profiles`.
- Владелец определяется токеном, а не присланным `owner_id`. Клиенты не могут менять ID, владельца, `request_id` или служебные даты. Удаление через API не разрешено.
- Каталог читает только `published_tasks`. В этом представлении нет черновиков, `owner_id`, `request_id`, `original_description`, `analysis_snapshot` и `business_contact`. Оно допускает только `SELECT` для `anon` и `authenticated`.
- `task_workspaces` никогда не публикуется: чтение, вставка и изменение разрешены только владельцу с ролью `business`. Посетители, студенты и другие бизнес-пользователи не имеют доступа к чужим вопросам и ответам. Токены, пароли и ключи в `snapshot` не сохраняются; API проверяет разрешённые поля.
- Остальные поля карточки после публикации становятся публичными. Не указывайте в них пароли, ключи и другую закрытую информацию. Контакт помещайте в отдельное поле `business_contact`, а не в публичное описание.

`published_tasks` намеренно работает с правами владельца `postgres`, а не вызывающего пользователя: это позволяет оставить исходную таблицу полностью закрытой для посетителей и отдавать только перечисленные безопасные колонки опубликованных записей. Включён `security_barrier`, публичные права записи отозваны. Supabase Security Advisor может отметить такое представление как `security_definer_view`; это известное исключение этой схемы, которое нужно учитывать при её изменении. Не добавляйте в представление приватные колонки и не заменяйте список колонок на `SELECT *`. Механизм прав представлений описан в [PostgreSQL CREATE VIEW](https://www.postgresql.org/docs/current/sql-createview.html); обычные представления без такого намеренного ограничения следует создавать с `security_invoker`, как рекомендует [Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security#views).

## Проверка после применения

1. Войдите под бизнес-пользователем, начните создание задачи, получите вопросы AI и введите ответы. После сохранения рабочего состояния и обновления страницы ответы должны восстановиться. Создайте карточку и сохраните черновик: он должен остаться в «Моих задачах» после обновления страницы, но отсутствовать в публичном каталоге.
2. Разместите задачу: она должна появиться в каталоге, в том числе после выхода из аккаунта и обновления страницы.
3. Повторная отправка того же черновика не должна создавать вторую запись.
4. После сохранения первой задачи начните новую, затем снова откройте первую в «Моих задачах»: её вопросы и ответы должны восстановиться независимо от новой рабочей сессии.
5. Другой бизнес-пользователь не должен видеть чужой черновик или изменять чужую задачу. Студент может читать каталог, но не публиковать задачи.
6. Проверьте в Table Editor сохранённые поля. Публичные запросы к `published_tasks` не должны возвращать исходный приватный текст, `analysis_snapshot` и контакты; запрос анонимного клиента к `tasks` должен быть запрещён.

Для чтения без изменения данных в SQL Editor:

```sql
select id, status, title, created_at, published_at
from public.tasks
order by created_at desc;

select id, title, description, published_at
from public.published_tasks
order by published_at desc;

select owner_id, updated_at, snapshot -> 'version' as snapshot_version
from public.task_workspaces
order by updated_at desc;
```

SQL Editor под `postgres` обходит RLS, поэтому сам по себе не доказывает разграничение пользователей. Проверяйте эти сценарии в приложении с разными аккаунтами. Если API сообщает, что таблица или представление не найдены, сначала примените SQL именно в том Supabase-проекте, URL которого указан в `.env`.
