# Анализ задачи через OpenAI

## Запуск

1. В `apps/api/.env` задать `OPENAI_API_KEY` и при необходимости `OPENAI_MODEL`
   (по умолчанию `gpt-4.1-mini`). Файл исключён из Git. Секрет не должен иметь префикс `VITE_`.
2. Настроить Supabase и после миграции `profiles` применить миграции `20260923000200_tasks.sql`
   и `20260923000300_task_workspaces.sql`: [инструкция](task-persistence.md).
3. Запустить `npm run dev` (или `dev:full`), войти под бизнес-пользователем и открыть
   `http://127.0.0.1:3000/#/create`.
4. После изменения `.env` перезапустить API-сервер.

AI всегда использует настоящий OpenAI Responses API. Mock и автоматический
fallback на шаблоны удалены. Переключатель `VITE_AI_MODE` больше не используется.
Каталог также всегда работает через API и Supabase; переключателя на mock нет.

## Flow

Описание → серверный запрос OpenAI → выбранное моделью количество вопросов (минимум 3, обычно 6–10 или больше) →
ответы → второй запрос OpenAI с исходным описанием и всеми ответами →
редактируемая карточка → «Принять результат» → редактор → сохранение черновика или публикация.
Публикация остаётся отдельным ручным действием. До неё описание, вопросы, ответы и результат
автоматически сохраняются в приватной рабочей сессии Supabase. Перед запуском анализа приложение
проверяет, что текущее состояние синхронизировано; если таблицы ещё не созданы, сначала выполните SQL.

Оба запроса используют Structured Outputs с JSON Schema. Сервер проверяет
входные данные и результат. Системные инструкции запрещают придумывать факты;
неизвестные поля возвращаются как null и перечисляются в missingInformation.
Пользователь проверяет достоверность карточки перед принятием. Данные запроса
передаются в OpenAI; параметр Responses `store` установлен в false.

## API

- `POST /api/ai/task-analysis/questions`, JSON `{description}` →
  `{data: {knownInformation, missingInformation, questions: [{id, field, text, reason}]}}`.
- `POST /api/ai/task-analysis/generate`, JSON `{description, questions, answers}` →
  `{data: {title, context, need, users, data, constraints, expectedResult,
successCriteria, businessContact, interactionFormat, missingInformation}}`.

Каждый AI-запрос требует `Authorization: Bearer <access_token>` текущего пользователя.
Backend проверяет токен через Supabase Auth и роль `business` из `profiles` до обращения к OpenAI.
Без входа возвращается 401, для студента — 403. Присланным полям роли и владельца сервер не доверяет.

Ключ используется только сервером в `apps/api/src/modules/task-analysis/service.js`.
Ответы об ошибках не раскрывают ключ или исходные сообщения провайдера.
Обрабатываются неверный ключ, отсутствие настройки, лимиты OpenAI, отказ модели,
некорректный JSON, пустой результат и таймаут. Сервер ждёт до 60 секунд,
frontend — до 75 секунд. При закрытии соединения сервер отменяет запрос OpenAI.
Ошибки не заменяются демонстрационным результатом; ответы пользователя сохраняются
для повторной попытки. Ограничения ввода: описание 20–10 000 символов, каждый
ответ до 10 000 символов, HTTP body до 128 KiB.

## Состояние и БД

Проект использует JavaScript, Vite и Tailwind, без React/TypeScript.
Состояние интерфейса хранится в store (`state.taskAnalysis`), типы — JSDoc. Выделенный
`features/tasks/workspace-controller.js` загружает и автоматически сохраняет явный снимок через
`GET/PUT /api/task-workspace` в приватную `task_workspaces`. Изменения отправляются после небольшой
паузы ввода; перед переходом к следующему AI-запросу выполняется синхронизация. Дождитесь статуса
успешного сохранения перед закрытием вкладки: последние ещё не отправленные изменения могут потеряться.

Снимок содержит исходное описание, вопросы, ответы, текущий шаг, результат AI, ручные правки,
категории и оценку. Он восстанавливается после обновления страницы под тем же аккаунтом.
На пользователя хранится одна активная рабочая сессия. При сохранении черновика или публикации
анкета дополнительно архивируется в приватном `tasks.analysis_snapshot` конкретной задачи:
создание новой не стирает ответы уже сохранённых задач. Открытие задачи через «Мои задачи»
восстанавливает её анкету. Сохраняется последний снимок каждой задачи, не журнал всех версий.
Пароли, токены и произвольный store в JSON не попадают. При выходе приватное состояние памяти
очищается; запоздалый ответ старого запроса не должен заменять данные нового аккаунта/задачи.

`onAnalysisAccepted(result)` в `features/tasks/analysis-controller.js` передаёт
результат в `state.acceptedAnalysis` и `state.fields`, затем открывает editor.
Дальнейшие ручные правки находятся в `state.fields`; публикация берёт актуальные значения оттуда,
а не первоначальный AI-ответ. `save-draft` и `confirm-publish` вызывают `POST /api/tasks`:
итоговая карточка сохраняется в `tasks` с владельцем из токена и статусом `draft`/`published`.
После успешной записи «Мои задачи» и публичный каталог обновляются с сервера.
Повторная отправка с тем же `requestId` не создаёт дубль.

Черновики, исходный текст, ответы AI и `business_contact` доступны только владельцу.
Каталог читает `published_tasks`: публичные поля опубликованной карточки без этих приватных данных.
Вопросы/ответы остаются в рабочем снимке и приватном архиве своей задачи,
а не становятся публичной частью карточки.
Результат AI может пересказывать введённую информацию: проверяйте публичные поля перед публикацией
и не переносите в них контакт, ключи или другие секреты. Удаление задач, команды, отклики и избранное
пока не имеют полноценного серверного workflow.

## Проверки

`npm run check`: ESLint, тесты и production build. Автотесты используют подмену
сетевого транспорта и не расходуют API-кредиты. Они проверяют ошибки, права доступа,
передачу вопросов/ответов, сохранение и восстановление состояния и защиту от запоздалых запросов.
SQL проверяется отдельно локально; реальные записи в Supabase пользователя и платные запросы
OpenAI не создаются автоматически этими тестами. После применения миграций выполните
[ручную проверку сохранения](task-persistence.md#проверка-после-применения) своим аккаунтом.

Официальный формат запросов: [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

## AI-Scoring

После принятия результата и после каждого сохранения правки редактора вызывается
`POST /api/ai/task-analysis/score` с `{card}` (актуальные десять полей карточки).
OpenAI оценивает качество по семи критериям: проблема 20, пользователи 10,
данные 15, результат 15, успех 20, ограничения 10, взаимодействие 10.
Сервер проверяет баллы и суммирует их до 100. Заполненность или длина текста
сами по себе баллов не дают. Ответ содержит `{data: {score, summary, criteria}}`,
каждый критерий — `{id, label, score, maxScore, explanation, recommendation}`.
UI показывает пояснения и рекомендации, загрузку и повтор при ошибке. Старые
ответы не заменяют новую оценку при параллельных правках. Ошибка оценки не
удаляет карточку и не заменяется локально рассчитанным рейтингом.

Количество вопросов определяет OpenAI: минимум три, предпочтительно больше пяти.
Модель может выбрать 3–5 вопросов для уже подробного описания. Сохраняемый рабочий снимок
допускает до 100 вопросов и занимает не более 256 КиБ; ограничения HTTP body и токенов также действуют.
Оценка сохраняется вместе с карточкой и рабочим состоянием, но не используется для выдачи прав доступа.
