# Первый этап Supabase: регистрация

В форме `apps/web/src/pages/auth.js` есть имя, email, пароль и роль `business` / `student`.
Регистрация и вход подключены к Supabase SDK. Зарегистрированный пользователь подтверждает почту,
затем входит; backend проверяет сессию и загружает профиль из `public.profiles`.

## Таблицы и колонки

Supabase уже содержит управляемую таблицу `auth.users`: она хранит идентификатор,
email и данные аутентификации. Свою таблицу паролей создавать не нужно.

Добавляем `public.profiles`:

| Колонка      | Тип         | Назначение                                              |
| ------------ | ----------- | ------------------------------------------------------- |
| `id`         | uuid        | Тот же ID, что у пользователя Supabase Auth; PK + FK    |
| `full_name`  | text        | Имя из формы, от 1 до 120 символов без крайних пробелов |
| `role`       | text        | Выбранный тип аккаунта: business или student            |
| `created_at` | timestamptz | Время создания профиля                                  |
| `updated_at` | timestamptz | Время последнего изменения                              |

Для регистрации отдельные таблицы компаний/команд не требуются: форма не собирает
сведения об организации, университете или составе команды. Для дальнейших экранов
понадобятся companies, teams, team_members, tasks, proposals и saved_tasks;
их структура и политики доступа добавляются отдельными миграциями.

## SQL

Файл: `supabase/migrations/20260923000100_registration_profiles.sql`.
Откройте SQL Editor нового Supabase-проекта, вставьте весь файл и выполните один раз
под владельцем базы `postgres`. Миграция не удаляет существующие объекты. Если таблица
`profiles` уже существует, сначала нужна отдельная миграция под её текущую структуру.

Если таблица и триггеры уже созданы, этот SQL повторно запускать не нужно.

## Как работает кнопка

Обработчик регистрации вызывает Supabase Auth:

```js
const { data, error } = await supabase.auth.signUp({
  email: email.trim(),
  password,
  options: {
    data: {
      full_name: fullName.trim(),
      role, // business или student
    },
  },
});
```

Клиент SDK создаётся в `apps/web/src/shared/supabase.js`, значения читаются через FormData.
Клиент проверяет имя и роль до запроса; ограничения БД повторно проверяют эти данные.
Кнопка отключается на время запроса; ошибки и инструкция о подтверждении показываются в форме.

Триггер автоматически создаёт профиль. Дополнительный вызов `.from('profiles').insert()`
не нужен и для браузерного клиента запрещён. Ошибка триггера отменяет регистрацию,
поэтому `full_name` и `role` обязательны в metadata. Это касается и создания пользователей
через Dashboard или OAuth, пока для них не добавлен отдельный сценарий заполнения профиля.

При включённом подтверждении email `data.session` после регистрации может быть `null`:
показываем просьбу подтвердить почту, не открываем кабинет и не читаем защищённый профиль
до появления сессии. После входа профиль можно прочитать по ID пользователя.

RLS разрешает чтение только своего профиля. Через клиентский API можно менять только
`full_name`; роль и служебные поля защищены правами на колонки. Выбранная роль — тип аккаунта,
а не подтверждение компании. Для дальнейших проверок доступа используйте `profiles.role`,
а не изменяемый пользователем `user_metadata.role`.

## Окружение и запуск

В `apps/web/.env.local` нужны `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`.
В `apps/api/.env` нужны `SUPABASE_URL` и `SUPABASE_PUBLISHABLE_KEY` того же проекта.
Legacy anon key поддерживается через переменные `VITE_SUPABASE_ANON_KEY` / `SUPABASE_ANON_KEY`.
Секретный/service_role ключ не используется. Значения `.env` исключены из Git.

В Supabase → Authentication → URL Configuration настройте Site URL на `http://localhost:3000`
и добавьте `http://localhost:3000` и `http://127.0.0.1:3000` в Redirect URLs. Для других портов
нужно разрешить соответствующие адреса. При публикации добавьте URL сайта.

`npm run dev` запускает оба приложения. Для отдельных терминалов: `npm run dev:api`
и `npm run dev:web`. Изменения `.env` требуют перезапуска процессов.

Сессия сохраняется SDK между перезагрузками. Перед открытием кабинета backend обрабатывает
`GET /api/auth/me` с Bearer access token: вызывает `auth.getUser(token)` и читает свою строку
`profiles` с этим же токеном. В ответе только `{ data: { user: { id, email }, profile } }`.
Вход использует роль из проверенного профиля. При недоступности backend кабинет не открывается;
можно повторить проверку кнопкой в форме. Выход завершает текущую сессию Supabase.

Регистрацию на живом проекте следует проверить своим email: выполнить signup, подтвердить письмо,
войти, обновить страницу, проверить имя/роль в профиле, выйти. Автотесты используют подставной SDK
и проверяют эти сценарии без создания пользователей или отправки реальных писем.
