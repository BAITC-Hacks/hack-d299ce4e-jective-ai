# Отклики студентов

Отклик из формы «Предложить решение» хранится в `public.proposals` в Supabase. Это отдельные приватные данные, не часть публичного каталога задач. Backend обращается к базе с токеном текущего пользователя; `service_role` не требуется.

## Подключение

В Supabase → SQL Editor выполните целиком миграции **по одному разу**:

1. `supabase/migrations/20260923000400_proposals.sql` — таблица откликов; после миграций профилей `001`, задач `002` и черновиков `003`.
2. `supabase/migrations/20260923000500_proposal_decisions.sql` — статусы и решения бизнеса; после `004`.

Если таблица откликов уже создана, выполните **только новую миграцию `005`**. Ранее выполненные миграции повторно запускать не нужно. Миграция решений добавляет колонки в существующую таблицу, сохраняя все отклики: исходный статус — `pending`, дата решения — `null`. Таблица файлов `task_attachments` к этим миграциям не относится. Демо-отклики, решения и счётчики не добавляются.

После применения перезапустите приложение через `npm run dev`. Применение SQL к удалённой базе не выполняется автоматически при запуске приложения.

## Сохраняемые поля

| Поле формы         | Колонка         | Ограничение                                                       |
| ------------------ | --------------- | ----------------------------------------------------------------- |
| Задача             | `task_id`       | Существующая опубликованная задача                                |
| Название команды   | `team_name`     | 1–200 символов                                                    |
| Идея решения       | `idea`          | 1–10 000 символов                                                 |
| План реализации    | `plan`          | 1–10 000 символов                                                 |
| Сроки              | `deadline`      | 1–200 символов                                                    |
| Ссылка на прототип | `prototype_url` | Необязательно; HTTP(S), до 2048 символов, без логина/пароля в URL |

`id`, `student_id` и `created_at` задаёт база. Клиент не может подставить другого студента, идентификатор отклика или дату отправки. Пустая ссылка сохраняется как `null`; пробелы по краям полей удаляются. Backend дополнительно проверяет содержимое и разбирает ссылку стандартным URL-парсером. Сервер не скачивает содержимое ссылки.

После миграции `005` сохраняются также `status` (`pending`, `accepted`, `rejected`) и `decided_at` — серверная дата последнего изменения решения. Студент получает текущий статус своего отклика из Supabase, а не из заглушки браузера.

## Доступ и повторная отправка

- Только вошедший студент может отправить отклик на опубликованную задачу.
- Студент видит свои отклики, но не предложения других студентов.
- Бизнес видит все поля откликов только на свои задачи в разделе «Отклики».
- Гости и другие компании не имеют доступа. Публичный каталог не получает текст отклика.
- Проверяется роль из защищённого `profiles`, а не роль, переданная браузером. SQL-права и RLS действуют также при прямом обращении к Supabase REST API.
- На одну задачу один студент может отправить один отклик. Повтор идентичной отправки возвращает уже сохранённый отклик; попытка заменить его другим содержимым возвращает конфликт. Для новой версии необходим отдельный явно спроектированный процесс редактирования.
- Текст, автор, задача и дата отправки неизменяемы. `DELETE` недоступен клиентским ролям. Обновлять разрешено только `status`, только бизнесу-владельцу задачи; студент не может принять собственный отклик.
- Удаление задачи или аккаунта её владельца администратором удаляет связанные отклики каскадно. Удаление аккаунта студента также удаляет его отклики.

## Решение бизнеса

В разделе «Отклики» бизнес-владелец может принять или отклонить предложение. Решение сохраняется в Supabase и отображается студенту в его откликах после загрузки данных. Новые отклики всегда начинаются со статуса «На рассмотрении» (`pending`); передать при отправке поддельное решение или дату нельзя.

Решение можно изменить с `accepted` на `rejected` и обратно. Вернуть отклик в `pending` нельзя. Повторное сохранение того же статуса не меняет дату решения. Принятие одного отклика не отклоняет остальные и не закрывает задачу автоматически.

API принимает `PATCH /api/proposals/:id/decision` с телом `{ "status": "accepted", "expectedStatus": "pending" }` (также доступно решение `rejected`). `expectedStatus` — статус, который бизнес видел перед нажатием: обновление фильтруется по нему, чтобы устаревшая вкладка не перезаписала более новое решение. При конфликте нужно обновить список и повторить осознанное действие. Права на задачу и роль проверяются и API, и политиками базы; клиент не передаёт бизнес-владельца или дату решения.

## Проверка после миграции

1. Под бизнес-аккаунтом опубликуйте задачу.
2. Войдите студентом, откройте задачу и заполните все поля формы «Предложить решение». Отправьте отклик.
3. Обновите страницу: отправленный отклик должен оставаться в личном разделе студента.
4. Снова войдите бизнесом-владельцем: в разделе «Отклики» должны быть команда, идея, план, сроки и ссылка.
5. Примите или отклоните отклик. После обновления страницы решение должно сохраниться. Войдите студентом-автором и проверьте тот же статус в его откликах.
6. В другом бизнес-аккаунте или другом студенческом аккаунте этот отклик недоступен. Студент не может менять решения бизнеса.

Основа модели доступа: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) и [права PostgreSQL на таблицы/колонки](https://www.postgresql.org/docs/current/ddl-priv.html).
