# Профили в откликах

Примените `supabase/migrations/20260923000400_task_proposals.sql` в SQL Editor после миграций регистрации и настроек профиля. Миграция повторяемая, существующие таблицы задач сторонних разработчиков не затрагивает: создаёт отдельные `business_tasks` и `task_proposals`. В рабочий проект автоматически не применялась.

Сценарий: бизнес принимает сформированную карточку → публикует → студент открывает задачу в каталоге → видит профиль заказчика и отправляет предложение → бизнес открывает «Отклики» и профиль студента → выбирает или отклоняет предложение. Студент видит результат в «Мои отклики». Отклики сохраняют ID задачи, отправителя и связь с владельцем через внешний ключ, не зависят от текущей открытой страницы или текста названия команды.

При настроенном подключении каталог показывает сохранённые опубликованные задачи, без демонстрационных карточек. Кнопка сохранения черновика по-прежнему относится к текущей сессии; публикация теперь сохраняется в базе. Приватные исходные вложения не публикуются и другим участникам не доступны. В задачу попадает принятая пользователем текстовая карточка.

Опубликованные задачи доступны для чтения всем посетителям. Публиковать может только бизнес от своего имени; отправлять отклики — студент от своего имени. Читать отклик могут его отправитель и владелец задачи, менять статус — только владелец задачи. Для одной задачи допускается один отклик от студента и одна выбранная команда. Роль, отправитель и задача отклика не меняются через клиент. Профили участников доступны зарегистрированным пользователям по ранее настроенным правилам.

Навигация: профиль открывается по нажатию блока аккаунта внизу боковой панели; на мобильном экране — по кнопке аккаунта в шапке. Вкладки «Профиль» и «Участники» убраны из главного меню; список участников по-прежнему доступен из профиля.

Проверки: `npm run check`, тесты `proposal-profiles.test.js`; SQL выполнен дважды в изолированном PGlite, проверены роли, приватность чтения, запрет чужих записей и решений, защита от повторных откликов и двух выбранных команд. Сквозная проверка в рабочем хранилище требует применения SQL.
