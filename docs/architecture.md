# Архитектура AI Sana

## Границы приложений

`apps/web` и `apps/api` — независимые npm workspaces. Общий пакет `@ai-sana/contracts`
содержит формат данных и чистые валидаторы; фикстуры используются только в тестах. Он не импортирует DOM,
серверные модули, конфигурацию окружения или секреты.

Поток чтения каталога:

```text
страница ← store ← catalog-controller ← frontend repository ← HTTP /api/tasks
                                                                  ↓
                         Supabase published_tasks ← repository ← service ← router
```

## Frontend

- `src/main.js` создаёт зависимости и соединяет их. Каталог всегда использует API; runtime-фикстур нет.
- `app/router.js` владеет hash-маршрутизацией: `#/catalog`, `#/detail?id=2`.
- `app/store.js` хранит состояние конкретного экземпляра приложения. Изменения выполняются через `update`;
  перерисовку вызывает контроллер или действие, а ввод в форму не теряется из-за автоматических обновлений.
- `app/events.js` связывает DOM-события с действиями features. Обработчики регистрируются один раз
  и снимаются при завершении экземпляра приложения.
- `pages` — чистые функции от состояния к HTML. Они не выполняют запросы и не меняют состояние.
- `components` — общие визуальные элементы. Они не импортируют страницы или контроллеры.
- `features/tasks/model.js` — фильтрация, сортировка, выбор задачи и вычисление уровня готовности.
- `features/tasks/repository.js` — HTTP-загрузка каталога, своих задач и приватного рабочего состояния;
  для защищённых запросов получает access token текущего пользователя.
- `features/tasks/publication-controller.js` — сохранение черновика, публикация, загрузка «Моих задач»
  и повторная отправка с устойчивым `requestId` без создания дублей.
- `features/tasks/workspace-controller.js` — загрузка и автосохранение одного приватного рабочего состояния
  на пользователя. Сохраняет явный DTO, не весь store: описание, вопросы, ответы, карточку, метаданные и оценку AI.
- `features/tasks/analysis-controller.js` и `scoring-controller.js` — реальные запросы AI,
  синхронизация состояния до запроса и защита от запоздалых ответов после смены аккаунта/задачи.
- `shared/api/client.js` — единая обработка HTTP, JSON, ошибок, отмены и таймаута.
- `features/auth/service.js` — Supabase signup/signin/signout и получение проверенного профиля через API.
- `features/auth/controller.js` — состояние входа, подтверждение email, восстановление сессии,
  обработка событий SDK и защита от запоздалых ответов после выхода.

Пароли не попадают в store и не передаются нашему API. Supabase SDK управляет токенами;
для `/api/auth/me`, приватных операций задач и AI клиент передаёт access token в заголовке Authorization.
Backend проверяет токен через `auth.getUser()` и читает роль из БД, а не из user metadata.
При смене аккаунта приватное состояние в памяти очищается; затем загружаются данные нового владельца.
Сохранённые в Supabase задачи не удаляются при выходе. Состояние запросов и таймеры не сохраняются;
прерванный анализ можно повторить с восстановленными ответами.

При добавлении страницы создайте функцию в `pages`, экспортируйте её через `pages/index.js`,
зарегистрируйте в router и добавьте название в `components/layout.js`.
При добавлении пользовательского действия создайте обработчик в соответствующем `features/*/actions.js`
и подключите его в `app/events.js`. Не помещайте сетевые запросы в HTML-шаблоны.

Все значения пользователя/API перед вставкой в HTML экранируются через `esc`.
`btn` и `badge` могут принимать доверенный HTML для иконок; внешний текст нужно экранировать до вызова.
DTO-валидаторы проверяют форму данных, а экранирование защищает именно HTML-контекст — это разные границы.

## Backend

`server.js` отвечает за окружение, порт и жизненный цикл процесса. `app.js` собирает HTTP-handler
и принимает зависимости; при импорте он не запускает порт. Это позволяет тестировать API отдельно.

В модуле задач:

- router разбирает URL и метод запроса;
- service проверяет входные/выходные DTO и авторизацию приватных действий;
- repository обращается к Supabase и преобразует строки БД в DTO.

`GET /api/tasks` и `GET /api/tasks/:id` читают `published_tasks` без пользовательского токена.
`GET /api/tasks/mine`, `POST /api/tasks`, `GET/PUT /api/task-workspace` сначала проверяют пользователя
через Supabase Auth и роль `business` из `profiles`, затем используют отдельный Supabase-клиент
с этим Bearer-токеном. Владелец не принимается из JSON клиента. При сохранении задачи уникальная
пара `(owner_id, request_id)` предотвращает дубликаты при повторе; тот же запрос обновляет существующую запись.
Запоздалый черновик не перезаписывает уже опубликованное содержимое — это защищено и в БД.
При сохранении API читает рабочую сессию проверенного владельца с совпадающим `requestId`
и копирует анкету в `tasks.analysis_snapshot`. Архив приходит только в DTO собственных задач
(`analysisSnapshot`), не в публичный каталог. Редактор восстанавливает анкету конкретной задачи из архива.

Все AI-endpoints также требуют проверенного бизнес-профиля **до** вызова OpenAI.
Привилегированный Supabase service key нигде не нужен. Правила доступа и бизнес-валидацию
добавляйте в сервис; работу с HTTP оставляйте в router. Возвращайте публичные DTO, а не полные строки БД.

Модуль `modules/auth` содержит защищённый `/api/auth/me`. Он создаёт отдельный Supabase-клиент
на запрос с пользовательским Bearer-токеном: RLS продолжает действовать, привилегированные ключи
не используются. Нет конфигурации — 503; неверная сессия — 401; нет профиля — 404;
недоступен Supabase — 503. Ошибки SDK не попадают в клиент или логи с заголовками.

Новые модули (например, отклики) добавляются рядом с задачами и подключаются в `app.js`.
Для записи нужны отдельные endpoints, валидация входных данных и проверка прав.
Приватные страницы защищены на frontend для навигации, а авторизация API выполняется на сервере.

## База данных и приватность

После существующей миграции профилей пользователь должен выполнить
`20260923000200_tasks.sql`, затем `20260923000300_task_workspaces.sql` в Supabase SQL Editor.
Приложение не создаёт таблицы автоматически и не подменяет отсутствующую БД демонстрационными данными.
Порядок установки — в [task-persistence.md](task-persistence.md).

- `tasks`: исходное описание, редактируемая карточка, категории, статус, оценка и серверные даты,
  а также приватный `analysis_snapshot` с вопросами и ответами каждой сохранённой задачи.
  Начало новой рабочей сессии не удаляет эти архивы; повторное сохранение задачи обновляет её снимок.
  RLS разрешает чтение своих записей; вставку и изменение — владельцу с бизнес-профилем.
  Права на отдельные колонки и триггер защищают владельца, ID, ключ повторной отправки и даты.
- `task_workspaces`: один приватный JSON-снимок на владельца, включая промежуточные вопросы и ответы AI.
  API проверяет разрешённые поля; БД проверяет объект, версию и размер до 256 КиБ.
  Авторизованный бизнес-пользователь может читать и менять только свою строку.
- `published_tasks`: явная публичная проекция опубликованных карточек, без исходного описания,
  контакта заказчика, ID владельца, `request_id` и `analysis_snapshot`. Только чтение;
  черновиков, архивов анкет и workspace в каталоге нет.

Публичное представление намеренно принадлежит `postgres` и использует права владельца с
`security_barrier`: исходная таблица остаётся закрытой для анонимного доступа, а представление
выдаёт только перечисленные публичные поля. Это осознанное исключение из обычного подхода
`security_invoker`, описанное в инструкции миграций; Supabase Security Advisor может его отметить.
Не добавляйте приватные поля или `SELECT *` в эту проекцию.

Оценка AI — информационная, не основание для разрешений. Не публикуйте секреты в остальных
полях карточки: они общедоступны после публикации. Отдельное поле контакта и ответы остаются приватными.
Команды, отклики и избранное пока не используют постоянное хранение.

## Договор между приложениями

`packages/contracts/src/index.js` документирует поля `Task` через JSDoc и экспортирует runtime-валидаторы.
Frontend проверяет ответы API на этой границе, backend формирует DTO через те же валидаторы.
Пакет можно впоследствии перевести на TypeScript независимо от выбранного UI-фреймворка.

Контракт успешного ответа: `{ data: ... }`. Контракт ошибки: `{ error: { code, message } }`.
Внутренняя ошибка логируется на сервере, но не передаёт клиенту stack trace или сведения о БД.

## Проверки и стиль

Перед изменением схемы обновляйте контракты и соответствующие тесты обоих приложений.
`npm run check` проверяет импорты/необъявленные переменные через ESLint, выполняет тесты Node
и собирает frontend. Тесты покрывают границу API, ошибочные ответы, авторизацию, публикацию,
синхронизацию рабочего состояния, загрузку и повтор каталога, фильтрацию, экранирование и рендер страниц.
Миграции отдельно проверены локально в PostgreSQL-движке на ограничения и RLS; это не заменяет
применение SQL и проверку сохранения в конкретном Supabase-проекте пользователя.

В проекте настроен Prettier. Сохранённые стили прототипа вынесены в `styles/legacy.css`;
новые стили можно добавлять отдельными файлами внутри слоя `components` или использовать Tailwind.
